# 仓库治理规则

## 仓库定位

`math-modeling-skill-pro` 是私有 Pro 主仓库，保存完整、已审核和可发行的核心资产。公共社区版必须在独立仓库维护，并从本仓库的白名单内容构建；不得通过修改本仓库可见性来发布社区版。

## 角色

| 角色 | 权限与职责 |
|---|---|
| Organization Owner | 管理仓库、成员、安全、许可证和发行决策 |
| Maintainer | 审查 PR、维护 Roadmap、处理 Issue 和发行准备 |
| Code Owner | 审查指定目录的内容质量、测试和权利边界 |
| Contributor | 在分支提交修改并响应审查，不直接推送 `main` |

只有长期、稳定、理解权利边界的贡献者才应获得仓库写权限。临时建议优先通过 Issue 提交，由维护者独立实现。

## 分支策略

- `main`：唯一长期分支，始终可通过验证并可构建；
- 功能和修复分支：短期存在，一个 PR 合并后删除；
- 不设置长期 `develop`，避免 Pro 内容在多个分支形成不一致真源；
- 禁止 Force Push 和删除 `main`；
- 所有修改必须通过 PR、自动检查和至少一次维护者审核。

## 当前托管限制与补偿控制

截至 2026-08-10，GitHub API 明确返回：当前组织套餐不支持在私有仓库上启用分支保护。为保护 Pro 内容，本仓库不得通过改为公开来绕过这一限制。因此，现阶段 `CODEOWNERS`、自动验证和本文件中的审查要求属于团队必须执行的流程规则，但 GitHub 尚不能在服务器端强制阻止管理员直接推送。

在套餐升级前，维护者必须执行以下补偿控制：

- 写权限仅授予确有持续协作需要的成员，不授予临时贡献者管理员权限；
- 修改一律从独立分支发起 PR，合并前人工确认 `validate` 成功；
- 至少一名非作者维护者或相关 CODEOWNER 审查内容、来源和权利边界；
- 只使用 Squash Merge，合并后删除源分支；
- 发布前从干净克隆重新运行完整验证并核对提交哈希；
- 发现绕过流程的直接推送时，立即暂停发行并补做等价审查。

套餐支持私有仓库保护后，应启用以下门禁：要求 `validate` 且分支保持最新、要求 PR 和至少一次批准、要求 CODEOWNER 审查、推送新提交后撤销旧批准、要求解决全部审查对话、要求线性历史，并禁止 Force Push 和删除 `main`。在至少有两名稳定维护者后，再将相同规则强制应用于管理员，避免单人维护阶段发生不可恢复的锁定。

## 合并标准

PR 只有在以下条件全部满足时才能合并：

1. 范围清晰并关联 Issue；
2. 自动验证通过；
3. 所有审查对话已解决；
4. 相关 CODEOWNER 批准；
5. 新案例具有可核验来源和证据边界；
6. 不包含原论文文件、近似长段、密钥或私人数据；
7. 索引、统计和文档同步更新；
8. 贡献授权复选框已确认。

## 发行

1. 从最新 `main` 创建发行候选；
2. 运行完整验证和版权清单；
3. 更新 `CHANGELOG.md` 和版本信息；
4. 创建签名或经维护者确认的 `vX.Y.Z` 标签；
5. 从干净克隆构建 ZIP；
6. 解压复验并生成 SHA-256；
7. 商业包、粉丝体验包和公共仓库分别使用独立清单。

## 公共社区版

公共版建议使用独立仓库 `math-modeling-skill-community`，只发布明确批准的代表案例、知识文档、模板和代码骨架。公开前必须单独确定许可证；任何已经进入公开 Git 历史的内容都应视为不可可靠收回。
